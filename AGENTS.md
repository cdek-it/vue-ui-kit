# Правила для оберток (wrappers)

Этот файл задает единые правила для компонентов-оберток в `vue-ui-kit`.
Обертка должна быть тонким слоем над исходным компонентом и не ломать его API без явной причины.

## Цели оберток

- Дать единый DX для команды (предсказуемые пропсы, слоты, поведение).
- Инкапсулировать проектные дефолты и стили.
- Сохранять предсказуемое поведение поверх upstream-компонента (`primevue` и др.) без протечки лишнего API наружу.
- Минимизировать объем собственной логики в обертке.

## Обязательные правила

### 0) Применение правил AGENTS

- Правила из этого файла обязательны для каждого изменения и имеют приоритет над временными workaround-решениями.
- Перед финализацией правок выполнять self-check по мини-чеклисту из этого файла и устранять расхождения до merge.
- После каждого значимого набора правок запускать как минимум `type-check` и `lint` (не откладывать проверки только на финальный этап).
- Каждая правка должна рассматриваться как потенциально релизная: не оставлять «временные» состояния между итерациями.
- Временные отклонения допустимы только на этапе диагностики; в итоговом состоянии они должны быть устранены или явно задокументированы.

### 1) Именование и размещение

- Имена: `Extra<ComponentName>` для prime-блоков.
- Путь: `src/primeBlocks/Extra<ComponentName>/Extra<ComponentName>.vue`.
- Экспорт должен быть добавлен в `src/primeBlocks/index.ts`.

### 2) API-совместимость

- Публичный API обертки задается в компонентной спецификации (spec-first) и является источником правды.
- Обертка принимает и документирует только spec-пропсы; upstream-пропсы не обязаны пробрасываться 1:1 наружу.
- Spec-пропсы должны быть описаны явно и буквально по спецификации компонента (имена/типы/union) в `types.ts`; публичный API обертки не должен формироваться через наследование, выборку или индексный доступ от upstream-типов.
- Публичные типы обертки должны быть самостоятельными: типы prop-полей задаются явно по спецификации, без привязки к внутренним типам upstream-компонента.
- Внутри обертки допускается маппинг spec-пропсов в upstream API (например, `size: sm|base|lg|xlg` -> `small|undefined|large|xlarge`).
- Если требуется backward compatibility, legacy-пропсы допускаются только как временный слой с явной документацией и сроком удаления.

Рекомендуемый шаблон:

```ts
interface IExtraX {
  // spec props
  size?: 'sm' | 'base' | 'lg' | 'xlg';
  labelPosition?: 'default' | 'float' | 'left';
}
```

### 3) Прозрачный проброс

- Пробрасывать в базовый компонент только нужные downstream-пропсы (явно или через контролируемый объект маппинга).
- Для item/action-паттерна объединять данные через helper-функцию (например, `getItemAttrs`).
- Не дублировать вычисления, которые уже делает upstream-компонент.
- Не создавать одноразовые `computed`-объекты для простого `v-bind`, если нет дополнительной нормализации/маппинга.

### 4) Слоты

- Пробрасывать стандартные слоты upstream-компонента.
- Кастомизацию обертки делать через fallback в слотах, без блокировки пользовательских слотов.
- Подключать только реально существующие слоты (проверять через типы `...Slots`).

### 5) Типизация

- Использовать `script setup` + TypeScript.
- Типы слотов получать из пакета компонента (например, `type XItemSlotProps = Parameters<...>[0]`).
- Не применять `any`, если можно выразить тип через upstream-типы.
- Не добавлять `computed`-обертки для пропсов с `withDefaults`, если нет дополнительной нормализации/маппинга.
- Spec-тип пропсов (и связанные `type`/`union`) выносить в отдельный `types.ts` рядом с компонентом и переиспользовать в сабкомпонентах.

### 6) Стили

- Обертка не должна вносить тяжелые стили по умолчанию.
- Локальные стили добавлять только при необходимости и документировать причину.
- Перед добавлением, переносом или удалением CSS проверять реализацию установленной версии Prime: какие стили, состояния, анимации и component-level токены она уже применяет. Не дублировать встроенные стили; оставлять только необходимую дельту относительно макета. Удалять переопределение только после проверки, что базовая реализация и текущие токены покрывают его поведение, с учетом различий в значениях и селекторах.
- Классы должны быть стабильными и предсказуемыми для переопределения.
- Не использовать `!important` в стилях оберток; конфликты решать специфичностью селекторов, порядком подключения и токенами.
- Стили, относящиеся к `Extra*` (например, `.extra-*`), размещать в самой обертке (`<style scoped>` + `:deep(...)`), а не в `theme3.0/components/css/*.ts`.
- В `Extra*`-обертках собственные классы wrapper-слоя именовать только с префиксом `extra-*`; внутренние классы upstream-разметки PrimeVue остаются `p-*` и используются только для таргетинга через `:deep(...)`.
- Wrapper-специфичные модификаторы размеров/состояний (например, `xlg`, кастомные layout-варианты) оформлять BEM-классами `extra-*` и описывать в самой обертке, а не через глобальные классы в upstream-слое.
- В обертке допустимы `:deep(.p-*)` селекторы только как контекстная дельта внутри конкретного `Extra*` (scoped, привязка к wrapper-root), без глобального изменения базового слоя Prime.
- Для компонентов, у которых есть `Extra*`-обертка, визуальные стили (`state/layout/size`) должны жить в самой обертке; одноименный upstream файл `theme3.0/components/css/<component>.ts` после полной миграции удаляется.
- Для `:deep(.p-*)` в обертках предпочитать переопределение CSS-переменных/токенов; прямые переписывания геометрии и состояний делать только при обоснованной необходимости.
- `theme3.0/components/css/*.ts` использовать для компонентов без `Extra*`-обертки и как временный bridge на этапе миграции; для компонентов с `Extra*` постоянным источником визуала является обертка.
- В одном `theme3.0/components/css/*.ts` файле не смешивать upstream-селекторы `.p-*` и wrapper-селекторы `.extra-*`.
- Изменения дизайн-токенов (цвета, состояния, семантика) вносить в `src/plugins/prime/theme3.0/**` (`tokens.json`, `CdekPreset.ts`, `components/css/*.ts`) и не дублировать их в legacy-слое `src/plugins/prime/theme/semantic.ts` без отдельной задачи.
- В задачах аудита и исправления компонентов запрещено изменять определения токенов: значения, алиасы/ссылки, размерные и тематические маппинги, а также добавлять токены ради совпадения с макетом. Запрет относится к `tokens.json`, генераторам/источникам экспорта, preset и другим слоям определения темы. Если подтверждённая цепочка Figma указывает на другой токен или значение, сообщать пользователю: компонент/вариант/режим, цепочка Figma, текущая цепочка в проекте и визуальное следствие. Самостоятельно не исправлять токен; изменение допустимо только по отдельному явному поручению пользователя на конкретное изменение токенов. Общее «исправить всё, что можно» таким поручением не является.
- При подтверждённом расхождении актуального макета и экспорта приоритет итогового визуала — у макета. Не блокировать исправление обёртки ожиданием нового экспорта: зафиксировать противоречие в текущем чате и реализовать минимальную контекстную CSS-адаптацию в соответствующей `Extra*`. Это явное исключение из приоритета component-токена и запрета локальной компенсации, но не разрешение изменять определения темы.
- Для такой адаптации сначала использовать существующий semantic-токен, цепочка и режим которого совпадают с макетом. Если подходящего токена нет, допустимо подтверждённое макетом literal-значение; размерные значения записывать в rem при базе 16px. Не переопределять `--p-*`, не менять preset/экспорт, не распространять исключение на другие компоненты/состояния. В CSS обязательно оставить комментарий `Design conflict DTC-...` со ссылкой на ID записи и причиной отступления от component-токена. Это документированная адаптация, а не исправление исходного токена.
- Запись противоречия должна содержать ID, дату, статус, компонент/вариант/состояние/тему/размер, версию или хеш экспорта, точное имя и полную цепочку Figma с режимами, JSON-путь и текущую цепочку/значение в проекте, ожидаемый и фактический визуал, применённую адаптацию и условие её удаления. Непроверенные привязки и противоречия внутри самого макета отмечать отдельно; не назначать им произвольное ожидаемое значение. Реестр противоречий хранить в текущем чате: включать прямые ссылки на конкретные ноды Figma и ссылки на локальные снимки/замеры вне репозитория. Не добавлять реестр, отчёты аудита, дампы computed styles, матрицы и скриншоты в git без отдельного явного поручения пользователя.
- После нового экспорта повторно проверять открытые DTC-записи. Удалять адаптацию только когда новый component-токен и реальный рендер покрывают её поведение; закрывать запись с указанием проверенного экспорта. Не удалять комментарий/историю противоречия без проверки и не переносить адаптацию автоматически на новую тему.
- При переносе стилей из `components/css/*.ts` в `Extra*`-обертку маппить `dt('token.path')` в `var(--p-...)` по kebab-case: `dt('inputtext.root.invalidBorderColor')` -> `var(--p-inputtext-invalid-border-color)`, `dt('inputtext.focusRing.width')` -> `var(--p-inputtext-focus-ring-width)`, `dt('inputtext.extXlg.paddingY')` -> `var(--p-inputtext-ext-xlg-padding-y)`.
- Для visual skin/state/size конкретного Prime-компонента в `Extra*` сначала использовать фактические component-level CSS vars (`--p-<component>-...`) как источник правды; не переходить на более общую ветку (`color.*`, `dimension.*`, `form.*`, `focusRing.*`) если есть эквивалентный токен на уровне компонента.
- Component-level токен обязателен, когда установленный Prime поддерживает соответствующую настройку через токен и эквивалентный токен задан в текущей теме. Если этого нет, разрешено напрямую использовать существующий semantic-токен, в том числе для skin Prime-компонента; не создавать дополнительные component-level алиасы только ради соблюдения префикса.
- Отсутствие component-токена или настройки Prime не является блокером визуальной правки. Проверять установленный Prime, затем реализовывать необходимую дельту кастомным scoped CSS в обёртке с существующим semantic-токеном. Если подходящего токена действительно нет, применять правило о допустимости обоснованных literal-значений ниже. Не оставлять подтверждённое расхождение только потому, что upstream наследует свойство или не предоставляет для него токен.
- До вывода «нельзя исправить» проверить доступные способы: корректность применения существующего component-токена, прямое использование semantic-токена при отсутствии component-настройки, необходимую контекстную CSS-дельту и, при подтверждённом отсутствии подходящего токена, допустимость документированного literal. Различать техническое ограничение, конфликт подтверждённых источников, непроверенную привязку и ещё не выполненную правку. Если правка разрешена текущей задачей, выполнять её без повторного согласования; не требовать нового экспорта или отдельной задачи только из-за отсутствия upstream API. При запросе только списка/анализа код не менять.
- Семантические токены (`--p-color-*`, `--p-dimension-*`, `--p-effects-*`, `--p-fonts-*`) использовать для wrapper-owned разметки и как прямой fallback при отсутствии подходящей component-level настройки/токена.
- Primitive-токены (`--p-colors-*`) в wrapper-стилях напрямую не использовать; если не хватает abstraction-level токена, сначала искать component-level, затем semantic, и только после этого обсуждать расширение темы.
- Если для wrapper-задачи не хватает токена, не менять базовую шкалу токенов, приходящую из Figma; локальную потребность закрывать существующим component-level/semantic токеном или отдельной задачей на расширение `theme3.0`.
- Сырые значения геометрии и типографики (`rem`, цвета, radius и т.п.) допустимы только когда подходящего токена в текущей теме реально нет и это явно подтверждено поиском/сборкой; в остальных случаях в обертках использовать `var(--p-...)`.
- Для токенов из ветки `extend` в `tokens.json` при переносе в `Extra*` ориентироваться на фактически доступное имя CSS var в компонентном префиксе (обычно без сегмента `extend`), и при расхождении проверять итоговое имя в сгенерированном CSS/Storybook перед merge.
- Если визуальная логика компонента полностью перенесена в обертку, соответствующий upstream `*.ts` файл удалить.
- Удалять upstream `theme3.0/components/css/<component>.ts` только после проверки, что визуал компонента полностью покрыт `Extra*`-оберткой и в docs-snippets/пользовательских примерах не осталось прямого использования соответствующего `primevue`-компонента.
- Для общих дочерних menu-компонентов (например, `ExtraMenuItem`) базовый layout и геометрия (`display`, `align-items`, `caption`, `icon/submenu` alignment) должны быть в самом компоненте.
- Обертки (`ExtraMegaMenu`, `ExtraMenubar`, `ExtraPanelMenu`) должны задавать только контекстную дельту через токены/переменные и не дублировать базовый layout child-компонента.

### 7) Документация и проверки

- Для новой обертки добавить Storybook-историю с базовым и кастомным сценариями.
- В docs-snippets и пользовательских примерах использовать импорты из текущей библиотеки (`@cdek-it/vue-ui-kit`) для компонентов, у которых есть `Extra`-обертка.
- Во внутренней реализации stories (template/meta файлы) допустим локальный импорт (`@/primeBlocks` или относительный путь).
- Если для компонента есть `Extra`-обертка, сами stories должны рендерить именно `Extra`-компонент (а не прямой `primevue` аналог).
- Если `Extra`-обертки для компонента нет, допустим прямой импорт из `primevue`.
- Для каждого значимого набора правок обязательны `type-check`, `lint`, smoke-проверка story.
- Проверка наличия CSS-переменных не подтверждает визуальное соответствие: после style-правок проверять computed styles и снимки реального компонента, включая focus/invalid/readonly, размеры и обе темы. Inline-стили preview не должны маскировать неработающие стили обертки. Для teleport-компонентов проверять scope на итоговом DOM; если scoped-контекст не сохраняется, допустимы документированные `:global(...)` селекторы, строго ограниченные собственным `.extra-*` root.
- При расхождении computed styles сначала находить выигравший селектор и его токен (например, `baseItem.padding` вместо `item.padding` у корневых пунктов меню); не повышать специфичность вслепую и не дублировать геометрию upstream в обертке.
- Для компонента с `Extra*`-оберткой Storybook-сториз живут только в `src/primeBlocks/Extra<ComponentName>/` и называются `Extra<ComponentName>.stories.js`. Upstream-папка `src/plugins/prime/stories/Form/<ComponentName>/` для такого компонента не создается; существующие upstream-сториз удаляются целиком, а уникальные кейсы (не покрытые Extra-сториз) предварительно переносятся в `Extra<ComponentName>.stories.js`. Если для `Extra*`-обертки сториз отсутствуют в `src/primeBlocks/`, они создаются там (переносом из upstream-папки) до ее удаления.
- Для правок стилей в `Extra*` после сборки проверять, что используемые `var(--p-...)` резолвятся в build-артефактах темы (`storybook-static`, нет неразрешенных/битых токенов).
- Проверку резолва `--p-*` выполнять через проектный скрипт (например, `yarn -s check:style-tokens` или эквивалентный шаг CI), а не только вручную.
- Если API отличается от upstream, описать отличие в документации компонента.

### 8) Figma как источник правды

- При визуальной сверке источником требований являются фактические стили конкретного целевого слоя и подтверждённые цепочки переменных/токенов с коллекциями и применёнными режимами. Текстовые правила, инструкции, Do/Don’t, блоки «Можно/Нельзя» и описания поведения в Figma считаются черновыми: не использовать их как основание визуальной правки, сообщения о конфликте дизайна или запроса решения пользователя. Противоречие текста стилям само по себе не является дефектом макета. Компонентные спецификации публичного API и правила этого AGENTS.md сохраняют силу.

- Storybook новой DS проверять при корневом размере шрифта 16px; не уменьшать rem-токены для компенсации старого масштаба 14px. При визуальном сравнении явно проверять computed `html.font-size`.
- Актуальный `theme3.0/tokens.json` из Figma рассчитан на 16px и является источником значений темы: не изменять и не перекрывать его значения отдельным preset/override-слоем ради подгонки оберток. Недостающие токены обсуждать отдельно, а не создавать скрытую параллельную шкалу.
- Перед объявлением токена отсутствующим или конфликтующим раскрывать полную цепочку алиасов Figma до конечного значения: свойство узла → привязанная переменная → её ссылки → конечный токен и значение. Проверять коллекцию и фактически применённый mode, включая унаследованный/Auto mode; значение одного режима не распространять на другие размеры и темы без проверки.
- Сопоставлять токены по цепочке ссылок и семантике, а не только по буквальному имени промежуточной переменной или совпадению чисел. Например, `form/fontSize` → `fonts/fontSize/200` может соответствовать существующему `fonts.fontSize.200` → `--p-fonts-font-size-200`; отсутствие `form.fontSize` в JSON само по себе не означает отсутствия нужного токена и не требует нового экспорта или алиаса. Фактическое имя CSS var и её значение подтверждать в сгенерированной теме и computed styles. Соблюдать приоритет component-level токенов из раздела 6; при отсутствии эквивалентной component-настройки использовать существующий semantic-токен напрямую.
- В записи `var(--form-fontSize, 14px)` число `14px` является fallback, а не доказательством значения переменной. Для вывода о соответствии проверять разрешённое значение в выбранном режиме. Считать конфликт источников подтверждённым только после проверки цепочки алиасов, режимов, маппинга экспорта и правил установленного Prime; не выдавать ошибку маппинга или hardcoded upstream default за неустранимый конфликт дизайн-токенов. Если цепочку или режим получить не удалось, фиксировать это как непроверенное условие.

- Для визуальных правок компонентов источник правды - Figma-макет (конкретный `fileKey` + `node-id`).
- Figma задает итоговый внешний вид, а не обязательную структуру верстки. Слои, вложенность и Auto Layout в макете могут не учитывать устройство PrimeVue: не копировать их в DOM и не перестраивать upstream-разметку ради структурного совпадения. Сохранять разметку, поведение и доступность Prime-компонента; обертка адаптирует только необходимую визуальную дельту. Критерий соответствия — видимый результат и состояния, а не совпадение контейнеров, названий слоев или способа раскладки. Изменения структуры допустимы только при подтвержденной необходимости для API спецификации, доступности или достижения итогового визуала.
- Выбор целевого узла в Figma делать через поиск по названию компонента в слоях (`MegaMenu`, `Menubar`, `PanelMenu`).
- Если текущее поведение компонента расходится с макетом, приоритет у макета, если нет документированной технической причины сделать иначе.
- Итоговый визуал обертки должен соответствовать целевому узлу Figma по ключевым состояниям/вариантам спецификации (например, `default/hover/focus/disabled/error`, размеры, `labelPosition`), если иное не зафиксировано в документации как осознанное отклонение.
- Для задач, завязанных на дизайн, использовать MCP-доступ к Figma. Внутренние ссылки на макеты и реестр противоречий сохранять в текущем чате; не добавлять их в репозиторий без отдельного явного поручения.
- Ссылку на макет запрашивать у автора задачи только в крайнем случае, когда узел нельзя надежно найти через MCP-поиск.
- Любые осознанные отступления от макета фиксировать в PR-описании и документации компонента.
- После обновления экспорта Figma-токенов, корневого размера шрифта, preset или версии PrimeVue повторно сверять все затронутые `Extra*`-обертки с актуальными узлами Figma. Предыдущее сравнение на другой версии темы или в другом масштабе не подтверждает текущий визуал.
- Запрос «проверить все обертки» начинать с полного списка экспортов `src/primeBlocks/index.ts`, включая общие дочерние компоненты. Выполнять сверку и публиковать матрицу результатов в рамках задачи, а не ограничиваться добавлением правила или запуском smoke. Недоступные в API варианты макета отмечать как отсутствующие, а не проверенные.
- При конфликте пиксельных замеров Figma и актуальных токенов при 16px сначала проверять целевой узел, версию экспорта, режим переменных и масштаб. Не нормализовать макет произвольным коэффициентом и не менять экспорт. Подтверждённое противоречие фиксировать в текущем чате отдельно от дефектов обёртки; итоговый визуал адаптировать к макету по правилам документированного DTC-исключения из раздела 6.
- Для сверки составлять матрицу оберток и вариантов: размеры, `labelPosition`, темы, `default/hover/focus/disabled/readonly/invalid`, сочетания состояний (например, `invalid + focus`), слоты и адаптивность — где они предусмотрены спецификацией. Каждый сценарий отмечать как проверенный, имеющий расхождение или непроверенный; не заменять матрицу одним базовым story.
- Сравнивать реальные `Extra*` в Storybook с Figma по геометрии, типографике, цветам, границам, отступам, иконкам и предусмотренным анимациям; фиксировать снимки и computed styles при 16px с загруженными шрифтами. В отчете указывать проверенные обертки/варианты, расхождения и ограничения, без внутренних ссылок на макеты в репозитории.
- После изменения font-size, line-height, padding или border измерять итоговую геометрию реального элемента через DOM и снимок. Для native form controls computed line-height не гарантирует такую же высоту строки или итоговую высоту поля: учитывать браузерное intrinsic sizing и метрики загруженного шрифта. Не объявлять ожидаемую высоту достигнутой только по сумме CSS-значений; оставшееся расхождение исследовать и исправлять в рамках разрешённой задачи либо точно фиксировать непроверенную причину/реальное ограничение, не объявляя его конфликтом токенов без доказательств.
- Успешные `type-check`, `lint`, сборка, резолв CSS-переменных и smoke подтверждают техническую работоспособность, но не соответствие макету. Заявлять «все обертки соответствуют макету» можно только после полной сверки заявленного набора; при недоступной Figma или непроверенных сценариях явно указывать, что визуальное соответствие не подтверждено.

## Антипаттерны

- Обертка с собственной бизнес-логикой вместо UI-адаптации.
- Скрытое изменение поведения upstream-компонента без документации.
- Проброс несуществующих слотов/пропсов (ломает типизацию и вводит в заблуждение).
- Использование в stories прямых импортов UI-компонентов из `primevue` вместо `Extra*` из библиотеки, когда обертка уже существует.
- Копипаст больших шаблонов вместо переиспользования `ExtraMenuItem`/общих хелперов.
- Реализация визуала "по памяти" или по скриншоту без проверки целевого узла в Figma.
- Хранение `Extra`-специфичных стилей в upstream `theme3.0/components/css/*.ts` после появления обертки.
- Параллельное хранение визуала одного и того же компонента в `Extra*` и `theme3.0/components/css/*.ts` после завершения миграции.
- Дублирование базового layout `ExtraMenuItem` в нескольких обертках вместо единого источника стилей в child-компоненте.
- Использование `!important` для фикса визуальных конфликтов вместо корректной структуры стилей.
