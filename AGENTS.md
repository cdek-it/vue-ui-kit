# Правила для оберток (wrappers)

Этот файл задает единые правила для компонентов-оберток в `vue-ui-kit`.
Обертка должна быть тонким слоем над исходным компонентом и не ломать его API без явной причины.

## Цели оберток

- Дать единый DX для команды (предсказуемые пропсы, слоты, поведение).
- Инкапсулировать проектные дефолты и стили.
- Сохранять предсказуемое поведение поверх upstream-компонента (`primevue` и др.) без протечки лишнего API наружу.
- Минимизировать объем собственной логики в обертке.

## Обязательные правила

### 0) Применение правил AGENTS

- Правила из этого файла обязательны для каждого изменения и имеют приоритет над временными workaround-решениями.
- Перед финализацией правок выполнять self-check по мини-чеклисту из этого файла и устранять расхождения до merge.
- После каждого значимого набора правок запускать как минимум `type-check` и `lint` (не откладывать проверки только на финальный этап).
- Каждая правка должна рассматриваться как потенциально релизная: не оставлять «временные» состояния между итерациями.
- Временные отклонения допустимы только на этапе диагностики; в итоговом состоянии они должны быть устранены или явно задокументированы.

### 1) Именование и размещение

- Имена: `Extra<ComponentName>` для prime-блоков.
- Путь: `src/primeBlocks/Extra<ComponentName>/Extra<ComponentName>.vue`.
- Экспорт должен быть добавлен в `src/primeBlocks/index.ts`.

### 2) API-совместимость

- Публичный API обертки задается в компонентной спецификации (spec-first) и является источником правды.
- Обертка принимает и документирует только spec-пропсы; upstream-пропсы не обязаны пробрасываться 1:1 наружу.
- Spec-пропсы должны быть описаны явно и буквально по спецификации компонента (имена/типы/union) в `types.ts`; публичный API обертки не должен формироваться через наследование, выборку или индексный доступ от upstream-типов.
- Публичные типы обертки должны быть самостоятельными: типы prop-полей задаются явно по спецификации, без привязки к внутренним типам upstream-компонента.
- Внутри обертки допускается маппинг spec-пропсов в upstream API (например, `size: sm|base|lg|xlg` -> `small|undefined|large|xlarge`).
- Если требуется backward compatibility, legacy-пропсы допускаются только как временный слой с явной документацией и сроком удаления.

Рекомендуемый шаблон:

```ts
interface IExtraX {
  // spec props
  size?: 'sm' | 'base' | 'lg' | 'xlg';
  labelPosition?: 'default' | 'float' | 'left';
}
```

### 3) Прозрачный проброс

- Пробрасывать в базовый компонент только нужные downstream-пропсы (явно или через контролируемый объект маппинга).
- Для item/action-паттерна объединять данные через helper-функцию (например, `getItemAttrs`).
- Не дублировать вычисления, которые уже делает upstream-компонент.
- Не создавать одноразовые `computed`-объекты для простого `v-bind`, если нет дополнительной нормализации/маппинга.

### 4) Слоты

- Пробрасывать стандартные слоты upstream-компонента.
- Кастомизацию обертки делать через fallback в слотах, без блокировки пользовательских слотов.
- Подключать только реально существующие слоты (проверять через типы `...Slots`).

### 5) Типизация

- Использовать `script setup` + TypeScript.
- Типы слотов получать из пакета компонента (например, `type XItemSlotProps = Parameters<...>[0]`).
- Не применять `any`, если можно выразить тип через upstream-типы.
- Не добавлять `computed`-обертки для пропсов с `withDefaults`, если нет дополнительной нормализации/маппинга.
- Spec-тип пропсов (и связанные `type`/`union`) выносить в отдельный `types.ts` рядом с компонентом и переиспользовать в сабкомпонентах.

### 6) Стили

- Обертка не должна вносить тяжелые стили по умолчанию.
- Локальные стили добавлять только при необходимости и документировать причину.
- Классы должны быть стабильными и предсказуемыми для переопределения.
- Не использовать `!important` в стилях оберток; конфликты решать специфичностью селекторов, порядком подключения и токенами.
- Стили, относящиеся к `Extra*` (например, `.extra-*`), размещать в самой обертке (`<style scoped>` + `:deep(...)`), а не в `theme3.0/components/css/*.ts`.
- В `Extra*`-обертках собственные классы wrapper-слоя именовать только с префиксом `extra-*`; внутренние классы upstream-разметки PrimeVue остаются `p-*` и используются только для таргетинга через `:deep(...)`.
- Wrapper-специфичные модификаторы размеров/состояний (например, `xlg`, кастомные layout-варианты) оформлять BEM-классами `extra-*` и описывать в самой обертке, а не через глобальные классы в upstream-слое.
- В обертке допустимы `:deep(.p-*)` селекторы только как контекстная дельта внутри конкретного `Extra*` (scoped, привязка к wrapper-root), без глобального изменения базового слоя Prime.
- Для компонентов, у которых есть `Extra*`-обертка, визуальные стили (`state/layout/size`) должны жить в самой обертке; одноименный upstream файл `theme3.0/components/css/<component>.ts` после полной миграции удаляется.
- Для `:deep(.p-*)` в обертках предпочитать переопределение CSS-переменных/токенов; прямые переписывания геометрии и состояний делать только при обоснованной необходимости.
- `theme3.0/components/css/*.ts` использовать для компонентов без `Extra*`-обертки и как временный bridge на этапе миграции; для компонентов с `Extra*` постоянным источником визуала является обертка.
- В одном `theme3.0/components/css/*.ts` файле не смешивать upstream-селекторы `.p-*` и wrapper-селекторы `.extra-*`.
- Изменения дизайн-токенов (цвета, состояния, семантика) вносить в `src/plugins/prime/theme3.0/**` (`tokens.json`, `CdekPreset.ts`, `components/css/*.ts`) и не дублировать их в legacy-слое `src/plugins/prime/theme/semantic.ts` без отдельной задачи.
- При переносе стилей из `components/css/*.ts` в `Extra*`-обертку маппить `dt('token.path')` в `var(--p-...)` по kebab-case: `dt('inputtext.root.invalidBorderColor')` -> `var(--p-inputtext-invalid-border-color)`, `dt('inputtext.focusRing.width')` -> `var(--p-inputtext-focus-ring-width)`, `dt('inputtext.extXlg.paddingY')` -> `var(--p-inputtext-ext-xlg-padding-y)`.
- Для оберток использовать фактические component-level CSS vars (`--p-<component>-...`) как источник правды; не переходить на более общую ветку (`form.*`, `focusRing.*`) если есть эквивалентный токен на уровне компонента.
- Для токенов из ветки `extend` в `tokens.json` при переносе в `Extra*` ориентироваться на фактически доступное имя CSS var в компонентном префиксе (обычно без сегмента `extend`), и при расхождении проверять итоговое имя в сгенерированном CSS/Storybook перед merge.
- Если визуальная логика компонента полностью перенесена в обертку, соответствующий upstream `*.ts` файл удалить.
- Удалять upstream `theme3.0/components/css/<component>.ts` только после проверки, что визуал компонента полностью покрыт `Extra*`-оберткой и в docs-snippets/пользовательских примерах не осталось прямого использования соответствующего `primevue`-компонента.
- Для общих дочерних menu-компонентов (например, `ExtraMenuItem`) базовый layout и геометрия (`display`, `align-items`, `caption`, `icon/submenu` alignment) должны быть в самом компоненте.
- Обертки (`ExtraMegaMenu`, `ExtraMenubar`, `ExtraPanelMenu`) должны задавать только контекстную дельту через токены/переменные и не дублировать базовый layout child-компонента.

### 7) Документация и проверки

- Для новой обертки добавить Storybook-историю с базовым и кастомным сценариями.
- В docs-snippets и пользовательских примерах использовать импорты из текущей библиотеки (`@cdek-it/vue-ui-kit`) для компонентов, у которых есть `Extra`-обертка.
- Во внутренней реализации stories (template/meta файлы) допустим локальный импорт (`@/primeBlocks` или относительный путь).
- Если для компонента есть `Extra`-обертка, сами stories должны рендерить именно `Extra`-компонент (а не прямой `primevue` аналог).
- Если `Extra`-обертки для компонента нет, допустим прямой импорт из `primevue`.
- Для каждого значимого набора правок обязательны `type-check`, `lint`, smoke-проверка story.
- Для правок стилей в `Extra*` после сборки проверять, что используемые `var(--p-...)` резолвятся в build-артефактах темы (`storybook-static`, нет неразрешенных/битых токенов).
- Проверку резолва `--p-*` выполнять через проектный скрипт (например, `yarn -s check:style-tokens` или эквивалентный шаг CI), а не только вручную.
- Если API отличается от upstream, описать отличие в документации компонента.

### 8) Figma как источник правды

- Для визуальных правок компонентов источник правды - Figma-макет (конкретный `fileKey` + `node-id`).
- Выбор целевого узла в Figma делать через поиск по названию компонента в слоях (`MegaMenu`, `Menubar`, `PanelMenu`).
- Если текущее поведение компонента расходится с макетом, приоритет у макета, если нет документированной технической причины сделать иначе.
- Итоговый визуал обертки должен соответствовать целевому узлу Figma по ключевым состояниям/вариантам спецификации (например, `default/hover/focus/disabled/error`, размеры, `labelPosition`), если иное не зафиксировано в документации как осознанное отклонение.
- Для задач, завязанных на дизайн, использовать MCP-доступ к Figma и не фиксировать внутренние ссылки на макеты в коде/документации репозитория.
- Ссылку на макет запрашивать у автора задачи только в крайнем случае, когда узел нельзя надежно найти через MCP-поиск.
- Любые осознанные отступления от макета фиксировать в PR-описании и документации компонента.

## Антипаттерны

- Обертка с собственной бизнес-логикой вместо UI-адаптации.
- Скрытое изменение поведения upstream-компонента без документации.
- Проброс несуществующих слотов/пропсов (ломает типизацию и вводит в заблуждение).
- Использование в stories прямых импортов UI-компонентов из `primevue` вместо `Extra*` из библиотеки, когда обертка уже существует.
- Копипаст больших шаблонов вместо переиспользования `ExtraMenuItem`/общих хелперов.
- Реализация визуала "по памяти" или по скриншоту без проверки целевого узла в Figma.
- Хранение `Extra`-специфичных стилей в upstream `theme3.0/components/css/*.ts` после появления обертки.
- Параллельное хранение визуала одного и того же компонента в `Extra*` и `theme3.0/components/css/*.ts` после завершения миграции.
- Дублирование базового layout `ExtraMenuItem` в нескольких обертках вместо единого источника стилей в child-компоненте.
- Использование `!important` для фикса визуальных конфликтов вместо корректной структуры стилей.

## Мини-чеклист на каждую правку

- [ ] Папка и имя соответствуют `Extra<ComponentName>`.
- [ ] Экспорт добавлен в `src/primeBlocks/index.ts`.
- [ ] Публичные пропсы соответствуют спецификации компонента (spec-first) и типизированы явно.
- [ ] Публичный API обертки не собран через наследование/выборку/индексный доступ от upstream-типов; spec-пропсы объявлены явно в `types.ts`.
- [ ] Публичные типы обертки самостоятельны: типы полей заданы явно по спецификации и не завязаны на внутренние типы upstream.
- [ ] Spec-типы вынесены в `types.ts` (когда это уместно) и переиспользуются в связанных сабкомпонентах.
- [ ] Для пропсов с дефолтами нет лишних `computed`, если значение не нормализуется.
- [ ] Нет одноразовых `computed`-объектов для простого прокидывания пропсов без нормализации.
- [ ] Слоты проброшены и проверены по `*Slots`.
- [ ] Нет лишней логики и тяжелых стилей в обертке.
- [ ] В стилях обертки не используется `!important`.
- [ ] `Extra`-специфичные стили находятся в обертке, а не в upstream `theme3.0/components/css/*.ts`.
- [ ] Для компонента с `Extra*` визуальные стили не дублируются между оберткой и `theme3.0/components/css/*.ts`.
- [ ] Wrapper-модификаторы размеров/состояний оформлены через BEM-классы `extra-*` в обертке, без глобальных `p-*` классов для wrapper-логики.
- [ ] Собственная разметка/классы обертки используют только `extra-*`; классы `p-*` не переименовываются и применяются только как upstream-слой через `:deep(...)`.
- [ ] `:deep(.p-*)` в обертке используются только как scoped-контекстная дельта для конкретного `Extra*`; глобальные изменения вынесены в `theme3.0/components/css/*.ts`.
- [ ] Если стили компонента полностью перенесены в обертку, legacy upstream `*.ts` файл удален.
- [ ] Перед удалением upstream `*.ts` проверено отсутствие прямых user-facing сценариев с `primevue`-компонента (docs-snippets/пользовательские примеры).
- [ ] Для общих child-компонентов (`ExtraMenuItem`) базовый layout находится в самом child, а обертки задают только контекстные переменные/дельту.
- [ ] Базовые стили общих child-компонентов параметризованы через CSS-переменные, а обертки переопределяют только эти переменные/контекстные токены.
- [ ] Для компонентов с `Extra`-оберткой docs-snippets и пользовательские примеры используют импорты из текущей библиотеки (`@cdek-it/vue-ui-kit`); во внутренних story-файлах допустим локальный импорт (если обертки нет, допустим `primevue`).
- [ ] Для визуальных правок целевой узел найден через MCP-поиск по слоям/названию компонента (или есть явное объяснение, почему это невозможно).
- [ ] Для визуальных правок проверено соответствие реализации целевому узлу Figma по ключевым состояниям/вариантам; отклонения явно задокументированы.
- [ ] Добавлены/обновлены stories.
- [ ] Если менялись токены, правки внесены в `src/plugins/prime/theme3.0/**`; legacy `src/plugins/prime/theme/semantic.ts` не изменялся без явного запроса.
- [ ] При переносе стилей из theme css в `Extra*` проверен корректный маппинг `dt('...')` -> `var(--p-...)` (имена переменных подтверждены по текущей теме/сборке).
- [ ] Для style-правок в `Extra*` проверено на сборке, что все используемые `--p-*` переменные разрешаются в итоговом CSS.
- [ ] Пройдены `type-check` и `lint`.
